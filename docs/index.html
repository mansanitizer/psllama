PSllama

Local AI inference on a jailbroken PlayStation 5, through Vulkan.

PSllama is a homebrew PS5 application that runs language, vision, speech, image, video and robot-policy models on the console's GPU and serves them over an OpenAI-style HTTP API. It is built from llama.cpp, stable-diffusion.cpp and whisper.cpp, all sharing one ggml Vulkan backend on the Mesa RADV driver from the PS5_Vulkan project.

Status: experimental. Tested on one console (CFI-1208B, firmware 13.60). It needs a jailbroken PS5 and is not affiliated with or endorsed by Sony. Every number below was measured on that console; nothing here is a guarantee for other hardware or firmware.

Requirements

  • Console: a jailbroken PS5 with a payload loader. Tested on CFI-1208B, firmware 13.60.
  • Payloads on the console: an ELF loader (elfldr), an FTP server (ftpsrv) and ShadowMount+ to register and mount the app folder. shsrv (shell) and klogsrv (kernel log) are needed for development.
  • Build host: Linux x86-64 with the PS5_Vulkan toolchain and its RADV build, cmake, clang and glslc.
  • Storage: the application is about 115 MB. Models are 0.1 to 14 GB each.
  • Network: the server only answers clients on a Tailscale network (100.64.0.0/10) and requires an API key.

Memory to plan around: the console has 16 GB shared between CPU and GPU. The app gets a 12 GiB Vulkan heap plus about 2.3 GB on the CPU side, so a model and its working memory must fit in roughly 12 GiB.

How to install

There is no prebuilt package. These are the steps used during development; paths are relative to the repository.

1. Prepare the build host

  1. Set up PS5_Vulkan and build its RADV driver (tools/build-radv.sh). The driver ships as source, not as a prebuilt library.
  2. Check out the three engines at the revisions PSllama was developed against:
    ProjectRevision
    llama.cpp552f18f91
    stable-diffusion.cppf89d9b1
    whisper.cppd1be6fd
  3. Apply patches/llama.cpp/psllama-vs-552f18f91.patch to llama.cpp and copy ssm_scan_mamba1.comp into ggml/src/ggml-vulkan/vulkan-shaders/. Together they cover the sampler fix, the memory-budget override and the Mamba-1 GPU scan.

2. Build

  1. Cross-build llama.cpp with the Vulkan backend for the PS5, with -DGGML_MAX_NAME=160 and the multimodal library enabled. stable-diffusion.cpp needs the longer tensor names, and all three engines must share this one ggml build.
  2. Build stable-diffusion.cpp against that same ggml using app/sd/CMakeLists.txt.
  3. Build the application. The API key is given here and compiled in:
cd app
PSLLAMA_API_KEY="$(openssl rand -hex 32)" \
PS5_VULKAN_ROOT=/path/to/ps5-vulkan \
LLAMA_SOURCE=/path/to/llama.cpp \
LLAMA_BUILD=/path/to/llama.cpp/build-ps5 \
SD_SOURCE=/path/to/stable-diffusion.cpp \
SD_BUILD=/path/to/sd-build-ps5 \
WHISPER_SOURCE=/path/to/whisper.cpp \
OUT=$PWD/out/my-build \
bash ./build-gguf-vk-title.sh

The result is out/my-build/eboot.bin plus an sce_module folder. The build takes about a minute once the libraries exist.

3. Install on the console

  1. Create the app folder, for example /data/homebrew/PPSA99005/, and upload eboot.bin and sce_module/ to it over FTP.
  2. Add sce_sys/param.json (title id and name) and sce_sys/icon0.png (512×512). The app will not register without an icon.
  3. Reboot and re-jailbreak. ShadowMount+ registers app folders when it starts; registering a new title later in the same session failed for us.
  4. Create vk-env.conf in the app folder with these two settings:
GGML_VK_IGNORE_MEMORY_BUDGET=1
GGML_VK_SUBALLOCATION_BLOCK_SIZE=268435456

The first works around memory counters that only ever grow on this driver. The second (256 MB blocks) avoids allocation failures after switching models.

4. Add models

Upload model files into the app folder over FTP. The console sees that folder as /app0.

5. Start and check

Launch the app from the home screen, then, from a machine on the same Tailscale network:

curl -H "Authorization: Bearer $PSLLAMA_API_KEY" http://$PS5_HOST:8081/health

It reports which models are loaded. The first launch loads the default model, which takes about 100 seconds.

Usage

All endpoints need the Authorization: Bearer header. Chat follows the OpenAI format, so existing clients work by pointing them at the console.

EndpointPurpose
GET /healthWhat is loaded, and with which settings
GET /v1/modelsLanguage models in the app folder
POST /v1/models/loadLoad a language model; with "stream": true it reports progress
POST /v1/chat/completionsChat, streaming or not; accepts images as image_url parts when the model has a projector
POST /v1/images/generationsText to image; ref_images_b64 for editing, init_image_b64 for image to image
POST /v1/videos/generationsText or image to video; returns PNG frames
POST /v1/audio/transcriptionsSpeech to text from a WAV file
POST /v1/audio/speechText to speech, optionally in a reference voice
POST /v1/voice/chatOne spoken turn: speech in, streamed text and speech out
POST /v1/vla/actOne OpenVLA control step: a 224×224 image and an instruction in, seven action values out
# Chat
curl http://$PS5_HOST:8081/v1/chat/completions \
  -H "Authorization: Bearer $PSLLAMA_API_KEY" -H "Content-Type: application/json" \
  -d '{"messages": [{"role": "user", "content": "Hello"}], "max_tokens": 64}'

# Load a model with progress events
curl -N http://$PS5_HOST:8081/v1/models/load \
  -H "Authorization: Bearer $PSLLAMA_API_KEY" -H "Content-Type: application/json" \
  -d '{"model": "Qwen3-4B-Q4_K_M.gguf", "context_tokens": 4096, "stream": true}'

# Generate an image
curl http://$PS5_HOST:8081/v1/images/generations \
  -H "Authorization: Bearer $PSLLAMA_API_KEY" -H "Content-Type: application/json" \
  -d '{"model": "flux2-klein-4b", "prompt": "a red fox in fresh snow", "size": "768x768"}'

Only one request runs at a time. Image and video models take the whole GPU, so the language model is unloaded for them and reloaded on the next chat request. Speech models and a language model under 5 GB stay loaded together.

Findings

Things learned about this hardware and driver that shaped the code. The working log with dates, commands and dead ends is FINDINGS.md.

Memory

  1. The driver's memory-budget counters only grow. After a few model swaps they report zero free memory and loads fail although the heap is empty. GGML_VK_IGNORE_MEMORY_BUDGET=1 (a small patch) makes the backend ignore them.
  2. Each Vulkan allocation must be one contiguous range. The default 1 GiB blocks stop fitting after models of different sizes have come and gone. 256 MB blocks fixed it with no measurable speed change.
  3. Reading GPU memory from the CPU is very slow. For the memory types the GPU uses, the CPU writes at about 26 GB/s but reads at about 49 MB/s. Anything that copies results back to the CPU each token has to be kept small.
  4. A vision projector can ask for far more than it needs. Qwen2.5-VL's projector sizes its buffers for a 1288×1288 image at load time; beside a 7B model and two speech models that allocation failed and the app crashed. The server now frees the speech models first and caps images at 1,024 tokens.

Speed

  1. Text generation is limited by memory bandwidth, which is why time per token tracks file size so closely.
  2. Image generation is limited by compute. Z-Image-Turbo took the same time at Q8_0 and at Q4_K.
  3. Low-temperature sampling was twice as slow as it should be. The console's math library takes about 75 ns for expf when the result underflows, and a sampler calls it for every token in the vocabulary. Skipping the call below −104 fixed it.
  4. One long GPU submission is killed after about 10 seconds. Prompt evaluation is split into small batches, and large image decodes are tiled, to stay under that.

Model-specific

  1. A 4-bit KV cache breaks Qwen2.5-VL. With q4_0 it produces garbage or stops after a few tokens, even on text-only prompts; q8_0 and f16 are correct. Other models tested are fine at q4_0. The cause was not investigated.
  2. Mamba-1 ran at CPU speed until it got its own shader. The backend's state-space scan only handled Mamba-2, so every Mamba-1 layer bounced to the CPU (98 graph splits). A scan shader for Mamba-1 brought that to 2 splits and 160 tok/s at 1.4B.
  3. A long instruction prompt makes a vision model describe what it expects. Asked to describe a scene and choose an action in one prompt, Gemma 3 reported what the task wanted, not what the image showed. Separate "describe" and "decide" calls fixed the descriptions.
  4. A general vision model is a weak robot controller. With scripted arm motions and Gemma 3 or Qwen2.5-VL choosing the steps, 5 of 12 tasks completed (2 of 12 without the image). Both models picked the right object first and then failed to sequence or stop. OpenVLA, trained for the job, completed 23 of 30 on harder tasks.

Console and tooling

  1. The app can become unlaunchable until a reboot. The launcher then answers 0x80940033 ("Can't start the game or app"). It happened once after a crash and once after editing the app's registered name and icon. ShadowMount's log shows why nothing can be registered in that state: AppInstallTitleDir bridge unavailable.
  2. To rename the app, change param.json and icon0.png in the source folder only, uninstall it in ShadowMount (never "Delete source"), and reboot.
  3. The console's FTP server is unreliable for existence checks. SIZE answers for files that are not there, and NLST and MDTM are missing. Use LIST. It also decrypts executables on download, so a re-downloaded eboot.bin must be compared with the unsigned ELF.
  4. Only one process can read the kernel log. Two readers split the stream between them, so development uses a single recorder that writes to files.

Limitations and known issues

  • One request at a time, and one large model at a time.
  • The API key is fixed at build time; changing it means rebuilding.
  • No raw text-completion endpoint, so models without the ChatML prompt format cannot be prompted properly yet.
  • Switching from image or video work back to voice costs about 50 seconds.
  • A crash in the app can require rebooting and re-jailbreaking the console.
  • Video output is PNG frames; encoding into a clip is left to the client.
  • OpenVLA was evaluated on one suite with 30 episodes. Other suites, a wrist camera and action chunking are untested.
  • RWKV and Jamba have not been run.
